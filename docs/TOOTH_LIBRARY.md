# 专业牙库（``teeth/*.eoff``）解析

**日期**：2026-09-28。数据清洗线结束、主线切到 Crown Outer 之后的第一步：
先把专业牙库读进来。

代码：`app/importers/tooth_library/`（`eoff.py` + `library.py`，**纯 stdlib**）。
真实牙库在仓库之外，根目录由环境变量 `CROWNFLOW_TOOTH_LIBRARY_ROOT` 指定
（本机为 `D:\code\牙冠自动生成\数据\牙齿数据库`，从微信接收后复制到 `数据/` 下，
不进 Git）。

---

## 1. 牙库目录结构

```
<root>/
  teeth/<库名>/{lowerjaw,upperjaw}/<n>.eoff          n = 1..8（牙位序号）
  teeth/<库名>/{lowerjaw,upperjaw}/<n>-reduced-*.eoff 内冠 / 颊侧上瓷 / thimble
  metadata/<库名>/{lowerjaw,upperjaw}.xml            ToothBow：FDI 级位姿
  metadata/<库名>/preview*.png                       人工预览
  pontics/<库名>/{lowerjaw,upperjaw}/                桥体
```

三个库：`炼金王`、`超神2`、`洋溢-长夜同在`；共 224 个 `.eoff`，
**但只有 144 份唯一内容** —— `teeth/` 与 `pontics/` 之间有 80 对文件逐字节相同
（内容哈希对账）。模板清点必须按内容哈希去重，不能把 pontics 的重复文件当独立模板。
**Crown Outer 用纯 `<n>.eoff`**（完整解剖冠），带 `-reduced` 等后缀的是内冠/上瓷变体。

两套库的网格形态不一样（对 CrownOuter 的意义见 `template.py` 的分发逻辑）：

* **炼金王 / 洋溢-长夜同在**：带根牙形（封底），牙颈环来自标签位；
* **超神2**：**未封底的冠形**（teeth 下的网格底面开放，FDI46 底边界 111 顶点
  全部度数 2、构成单一闭环）——底边界本身就是牙颈边界，不需要根、不需要切分。
  它的 `pontics` 才是封底的。

已知的网格瑕疵：**炼金王 FDI46 有一个 82 顶点、周长 9.7mm 的小破洞**（且位于
轴向下半部）。所以牙颈边界来源的优先级是：**显式标签环优先，开放边界只作回退**
且回退时核验"周长 ≥ π×最小跨度"（环形截面下界）——否则那个破洞就会被当成牙颈线，
形变边界完全错掉。位置检查（"在下半部"）拦不住这种洞。

## 2. `.eoff` 二进制格式（已对账，非猜测）

```
偏移 0        b"OFF BINARY\n"                         11 字节
偏移 11       uint32 V, uint32 F, uint32 E             12 字节
偏移 23       V × 12   float32 x,y,z                   顶点
23 + 12V      F × 14   uint16 n(=3) + uint32 i0,i1,i2  三角面
之后          扩展段序列，每段 = 25 字节名字段（ASCII + \0 填充）
                                [+ uint32 长度 + 负载]   ← 只有部分段有
              最后一段名 = END_EXTENSION
```

对账依据（三个库 / 5 个文件一致，缺一不可）：

* 头部读出的 `E` 满足 **`E == 3F/2`**；
* 面记录里 `n` 字段**全部等于 3**（如 17392/17392），面索引**全部**落在 `[0, V)`；
* 段序列**恰好覆盖到文件末尾**；
* `VERTEX_FEATURE_LABELS` 的项数**恰好等于 V**。

最容易搞错的两点（现有单元测试专门守住）：
**面记录是 14 字节**（不是 12 也不是 16）—— `uint16 顶点数 + 3×uint32 索引`；
**段名字段是 25 字节定长**。

## 3. XML 给什么、不给什么

`<ModelTooth><Number>` 就是 **FDI 编号**（每颌 16 个，如 38…31、41…48），
每牙位给出 `Position`、`AxisOcclusal`、`AxisMesial` —— 即**牙位局部坐标系**。
约定与项目其它部分一致：**Z = AxisOcclusal（咬合/就位向），X = AxisMesial（近中向），
Y = Z×X**。

**不给牙颈线。** `BuccoocclusalCusp*` / `ContactPoint*` / `BuccalPoint` /
`BuccocervicalPoint` / `LingualPoint` / `LinguocervicalPoint` /
`AntagonistCuspContact*` 在这套牙库里**全部为 0**（实测 16/16 全零）。
所以牙颈线只能从 `.eoff` 的逐顶点标签拿（下一节）。

## 4. 逐顶点标签 = 牙颈线（本轮最有价值的发现）

`VERTEX_FEATURE_LABELS` 是逐顶点位标志。**其中若干位构成一维闭环**
（单一连通分量 + 每个顶点度数恰好 2 + 周长 25~43 mm）—— 那就是牙颈线/轮廓线。

判定用的是**纯几何判据**，不依赖对位含义的任何假设：

```python
from app.importers.tooth_library import find_margin_loop
cand, bits = find_margin_loop(mesh)     # 取不到就返回 None，绝不硬凑
```

### 位语义无文档，而且跨库不一致（32 牙位全扫的实测）

| 库 | 取到闭环的牙位 | 牙颈线位 | 另一个环 |
|---|---|---|---|
| **炼金王** | **32 / 32** | `0x800`（较低较短） | `0x400`（较高较长） |
| **洋溢-长夜同在** | **32 / 32** | `0x800` | `0x400`；上颌另有 `0x20000000` 与 0x800 几乎重合 |
| 超神2 | **14 / 32** | `0x800`（仅部分牙位） | 无 |

超神2 缺 18 个牙位（含 FDI46/36/11 与整个下颌），**用单一位与 3 位以内的所有
并集都找不到闭环** —— 它的标注本身不完整。

**这就是"第一颗牙固定用炼金王"的依据**：不是偏好，是另外两个库里有一个的标注
不能用。`test_real_library_chosen_library_covers_all_32_teeth` 把这条钉住。

### 为什么不能写死位号

如果按"`0x800` 就是牙颈线"去写下游代码，在超神2 上会静默拿到一个**错位的边界
条件**，形变会把冠拉断，而且不报错。所以下游必须先 `find_margin_loop` 并接受
`None`，而不是假定某一位存在。

## 5. 模板标准化（CrownOuter 第一步，已实现）

`app/geometry/crown_outer/template.py`：任一库的 FDI 模板 → 标准化对象
`CrownTemplate`（顶点表达在该 FDI 的牙位局部系、原点 = 牙颈环质心、
牙颈环顶点集、冠/根划分、咬合朝向）。两种牙颈边界来源自动分发：
标签环（带根牙形）优先，开放底边界（冠形网格）回退。
取不到任何一种、+Z 不是咬合向、环不是拓扑腰 —— 都直接报错。

FDI46 三个库的标准化结果 vs 患者 margin（`cf_d310209b58909a45`，
周长 35.75mm，来自冻结索引）：

| 模板 | 边界来源 | 颈环点数 | 颈环周长 | 冠高 | 与患者周长比 |
|---|---|---:|---:|---:|---:|
| 炼金王 | 标签环 0x800 | 146 | 33.93 mm | 7.43 mm | **1.054** |
| 洋溢-长夜同在 | 标签环 0x800 | 156 | 31.38 mm | 7.47 mm | 1.139 |
| 超神2 | 开放底边界 | 111 | 26.18 mm | 7.54 mm | 1.366 |

超神2 形态最直接（纯冠、无根），但对这个患者，炼金王的颈缘尺寸起点最接近
—— 均匀缩放这步的拉伸量最小。两个模板都通过同一接口可用，v0 主线用炼金王。
